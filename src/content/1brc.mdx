The [1 Billion Row Challenge](https://1brc.dev/#%F0%9F%92%AA-the-challenge) is a
test of pure processing throughput, measuring how fast you can read 1 billion
rows from a text file and compute the min, max, and mean for each of up to
10,000 weather stations. The problem is very open-ended and leaves plenty of
room for optimization along the way. I first caught wind of this challenge about
2 years ago, but I wanted to wait until I was better equipped to take it on.
Submissions have since closed, so I tested this against my own hardware: an
Intel Core i5-10400 processor (6 cores, 12 threads, 2.9 GHz, 4.3GHz boost
frequency), 16 GB of dual-channel DDR4 DRAM, rated for 3200 MHz, but limited to
2666 MHz since that's the speed officially supported by the processor. The
official entries were evaluated on a Hetzner AX161, a 32-core machine with 128
GB of RAM. That machine holds the entire input (14.29 GiB, or 15.34 GB) in page
cache several times over, whereas mine has less _regularly available_ RAM than
the file has bytes. Since I'm bottlenecked by I/O on this setup, I did most of
my testing and profiling against a smaller file of 270 million rows, roughly a
quarter of the full input. Below is the problem statement in case you aren't
familiar.

## Preface

One thing that I failed to consider before beginning this project is how big of
a role the page cache would play. In retrospect, it makes complete sense —those
pages that are fetched from disk are stored in RAM to prevent future accesses
from hitting disk. The biggest concept that I initially didn't understand was
that the page cache scales dynamically and can grow to fill almost all of the
physical RAM that isn't used by other processes. However, one look at the
available memory that I actually had using `free` revealed that I had much less
memory to work with than I initially anticipated: 15 GiB total, with only 14 GiB
of that actually being available on an idle machine, against an input file of
14.29 GiB (15.34 GB). There's no possible way for the entire file to be present
in the page cache, even without other processes running. During my initial
tests, as RAM filled up, any pages fetched from disk had to evict other clean
pages, even those that were read ahead by the kernel and had yet to be accessed,
requiring another major fault (trip to disk) when those pages are needed.

<div className="h-5" />

I did consider walking behind the scan with `madvise(MADV_DONTNEED)` to release
what I had already read, but that only tears down my own page table entries and
leaves the page cache pages resident.

<div className="h-5" />

Due to this, I decided to use a file with 270 million rows instead (3.86 GiB).
Still a lot of data to parse, but small enough to stay resident in the page
cache. This means that a warm run takes zero major faults and the challenge
becomes a sheer measure of parse speed.

<div className="h-5" />

## Naive Approach

My initial "naive" approach was deliberately unsophisticated. It followed a
blueprint that remained _mostly_ constant throughout my revisions — what changed
over time was how each step was carried out, not the steps themselves.

<div className="h-5" />

This iteration was multithreaded, splitting the file into one roughly equal
range of bytes per thread while ensuring that no row straddled a chunk. One
approach that I considered but never attempted was handing out work dynamically
to the threads. I believed that the coordination overhead would be too great
and, in theory, each thread should finish around the same time anyway. Below is
a brief outline of how each thread operated in this inital implementation.
Consider how each of the underlined phrases might be changed / improved upon in
future iterations:

<div className="h-5" />

1. The thread <Revisit>processes one line at a time</Revisit>, finding the
   delimiter with <Revisit>
   [`std::ranges::find`](https://en.cppreference.com/cpp/algorithm/ranges/find)
   and
   [`std::unreachable_sentinel`](https://en.cppreference.com/cpp/iterator/unreachable_sentinel_t)
   </Revisit>, since the semicolon is guaranteed to appear on each line.
2. Parse the station and the temperature, storing the temperature as a 16-bit
   integer, that value being $$\text{temperature reading} \times 10$$. Add each
   reading to <Revisit>a single, global `std::map`</Revisit> guarded by
   <Revisit>a global mutex</Revisit>, since every thread writes into the same
   table.
3. Track the running <Revisit>min and max with `std::min` / `std::max`</Revisit>
   alongside the sum and count for each station.
4. Once every thread joins, walk the table in sorted order and write each
   station's results to the output file.

<div className="h-5" />

On the smaller file, this took just under three minutes which isn't great. The
wall clock isn't necessarily the most interesting metric, however: the program
boasted a measly 0.53 instructions per cycle when we should be shooting for 2 or
more at least. `perf` revealed that my implementation spent more than 6x as long
inside the kernel (system time) as it did running its own code (user time). With
the file already warm in page cache, almost none of that system time is I/O, it
is the futex waiting. Every thread that loses the lock parks itself in a futex
wait, and every handoff back costs a trip through the scheduler. 270 million map
updates behind one lock means 270 million opportunities for a thread to block,
and the twelve threads I have available on my machine spent most of their time
doing exactly that, as seen by the 174 million context switches, at an effective
clock of 1.94 GHz. Nothing about the parse loop mattered yet.

## **Optimization 1**: Poor Man's Map

I think that the most glaring issue with the naive approach is the use of a
single source of state, protected by a mutex that twelve threads fight over. A
much better approach comes from noticing that none of that state needs to be
shared while the file is being read. The min and max computations are
associative in nature, and the mean across all readings for a station can be
extrapolated from the sum of its temperatures and the total number of readings,
both of which are associative too. This means that every thread can keep its own
table, keyed by station name, accumulating those four values as it processes its
own chunk of the file. The twelve tables can be merged once the last thread has
joined, removing the need for any synchronization between threads while the file
is being read.

<div className="h-5" />

The tradeoff with this approach is that we are trading memory for speed, since
the table now exists twelve times over. My first iteration reached for the
obvious container for this, `std::map`:

<div className="h-5" />

```cpp
struct Stats {
  int16_t min, max;
  uint32_t count;
  int64_t sum;
};

std::map<std::string, Stats> table;
```

<div className="h-5" />

`std::map` is the most natural choice for a container here, sorting the keys by
default, which is required for the final output. Merging the tables at the end
is cheap as well, since each thread's table holds at most 10,000 entries, so
folding all twelve into one costs at most 120,000 updates. The catch is that
each of the 270 million upserts completed while reading the file has to locate
its key by descending the tree, and the tree is only shaped that way to give me
an ordering I need exactly once, after the merge, to print 10,000 lines.

<aside className="mt-6 rounded-md border-l-4 border-amber-400 dark:border-yellow-500/70 bg-amber-50 dark:bg-yellow-900/30 p-4">
  **Aside: SSO**

<div className="mt-2" />

Limiting the station names to at most 15 bytes allows for the keys of the map to
be stored directly inside the string object via short string optimization (SSO),
bypassing a separate heap allocation for the characters themselves. The bytes of
the string now live in the node we've already loaded, so a key comparison never
has to chase a pointer and wait on another cache line.

</aside>

<div className="h-5" />

Inspired by [this talk](https://www.youtube.com/watch?v=h8TBLKyo7Rs), we can do
some napkin math to approximate how much space we'll actually use with this
approach:

- Each node is 32 bytes, 24 bytes for left, right, and parent pointers, 4 bytes
  for a red/black color field (defined as an
  [unscoped enum](https://stackoverflow.com/questions/8115550/what-is-the-size-of-an-enum-type-data-in-c)),
  and 4 bytes of padding.
- The string key is another 32 bytes per node.
- The struct used to keep track of the stats for each station is 16 bytes, as
  seen in the above sample.

  <div className="mt-2" />

  Note that the sum of the temperature readings needs to be 64-bits in the worst
  case where every reading is 99.9 at the same station. All 270 million rows
  landing on one station sums to approximately $$2.7 \times 10^{11}$$, which is
  greater than the maximum value of a `uint32_t`, $$4.3 \times 10^9$$.

<div className="h-5" />

One thing to note is that every node creation calls its own `operator new`, and
[glibc's allocator](https://stackoverflow.com/questions/62095835/glibc-malloc-implementation-bookkeeping)
prepends an 8-byte header and rounds the result up to a 16-byte boundary, so an
80-byte request occupies a 96-byte chunk. So, this means that, across all
threads, the maps allocate

<div className="h-5" />

$$
96 \times 10,000 \times 12 \approx 11 \text{ MiB}
$$

<div className="h-5" />

Eleven megabytes against 16 GB of RAM sounds like a small price to pay, however,
it is important to note that my machine only has 12 MiB of L3 cache that is
shared across all six cores. The twelve maps fill 92% of L3 without counting a
single byte of the input. Moving one level up and considering the L2 cache, it's
worse still: two threads share a core's 256 KiB L2 between two ~940 KiB trees,
so in practice every lookup misses L2.

<div className="h-5" />

If the requested value for a lookup is not in cache, odds are there will be more
than one cache miss as we descend the map. A red-black tree with 10,000 nodes
is, in the worst case, $$2 \times \lg (10000 + 1) \approx 26$$ levels deep, so
an access could pointer-chase all 26 nodes the allocator placed wherever it
pleased into cache. This isn't to mention the string comparisons at every level
that only make the operation costlier. 26 trips to L3 on each of 270 million
upserts is unacceptable.

<div className="h-5" />

The obvious response is to swap in `std::unordered_map` and stop paying for
ordering we don't need. However, I found that it barely helped, and I believe
this is mostly due to the fact that it is still a node-based container that uses
buckets to handle hash collisions. Determining the bucket index of an item
[relies on the division operation when the number of buckets isn't a power of two](https://en.cppreference.com/cpp/container/unordered_map).

<div className="h-5" />

Instead of pursuing a node-based structure for our key-value store, we can write
a much simpler table that lies contiguously in memory and avoids unnecessary
overhead guaranteed by the standard: a fixed-size array of slots, indexed by a
hash of the station name.

<div className="h-5" />

```cpp
struct alignas(32) Slot {
  char name[16]; // 15 bytes + null terminator
  int16_t min, max;
  uint32_t count;
  int64_t sum;
};

// one per thread, 16K slots for at most 10,000 stations
std::vector<Slot> table(1u << 14);
```

<div className="h-5" />

By reserving space for the vector upfront, we bypass the need to request extra
memory on every insert. A power-of-two capacity allows us to map a hash to a
slot using the bitwise and operation instead of division via
`hash & (capacity - 1)`.

<div className="h-5" />

With 10,000 stations in 16,384 slots, our load factor is
$$\alpha \approx 0.61$$. Using standard linear probing, finding a key that is
already present takes approximately
$$\frac{1}{2}(1 + \frac{1}{1 - \alpha}) \approx 1.78$$ probes. Those extra
probes are nearly free, though, since every slot is 32 bytes and aligned, so two
slots share a cache line and spatial locality means the next slot is usually
already present.

<div className="h-5" />

Continuing on the idea of napkin math, we see how the two structures compare per
station entry:

<div className="h-5" />

$$
\begin{array}{|l|r|r|}
\hline
 & \textbf{std::map} & \textbf{poor man's map} \\
\hline
\text{Bytes per station} & 96 & 32 \\
\text{Footprint per thread} & 937 \text{ KiB} & 512 \text{ KiB} \\
\text{Footprint, twelve threads} & 11 \text{ MiB} & 6 \text{ MiB} \\
\text{Share of L3} & 92\% & 50\% \\
\text{Loads per lookup} & 26 \text{ worst case} & \sim 1.8 \text{ expected} \\
\text{Key comparisons per lookup} & 26 & \sim 1.8 \\
\text{Allocations per thread} & 10{,}000 & 1 \\
\hline
\end{array}
$$

<div className="h-5" />

Now, with this new map, what was 26 dependent loads in the worst case collapse
into one or two, and the address of that load is known the moment the hash
lands, so the core can keep several rows' lookups in flight instead of stalling
on each one in turn.

One detail that I glanced over was the hash function that I opted to use: a
[64-bit fnv1a hash](https://www.isthe.com/chongo/tech/comp/fnv/), which XORs
each character of the station name into a 64-bit accumulator and multiplies by a
prime. My initial implementation resembled the following code snippet:

<div className="h-5" />

```cpp
static constexpr uint64_t hash(std::string_view sv) {
  uint64_t h = 14695981039346656037ull;
  for (unsigned char c : sv) {
    h ^= c;
    h *= 1099511628211ull;
  }
  h ^= h >> 32; // avalanche

  return h;
}
```

<div className="h-5" />

Note that the above constants are the "fnv1a" prime and offset basis, which
abide by some constraints that I do not understand myself. Also, it is worth
noting that the avalanche step at the end mixes the high bits down into the low
ones I index with. The important thing to note from this snippet is that we must
process each character in the station name serially, since each calculation
depends on the value from the previous. To bypass this, we can use the fact that
station names are $$\le 15$$ bytes, allowing us to store the ASCII values of the
characters in two 64-bit integers. Now, the number of operations needed to
compute a hash stops growing with the size of the key: a three character station
name now costs the same to hash as a fifteen character one. I also opted to use
a
[fmix64 hash](https://encode.su/threads/1747-Extremely-fast-hash#post_message_34156),
based off of murmurhash, to compute the hash in three multiplications and three
shifts:

<div className="h-5" />

```cpp
static constexpr uint64_t hash(uint64_t s0, uint64_t s1) {
  uint64_t h = s0 ^ (s1 * 1099511628211ull);
  h ^= h >> 33;
  h *= 0xff51afd7ed558ccdull;
  h ^= h >> 33;
  h *= 0xc4ceb9fe1a85ec53ull;
  h ^= h >> 33;
  return h;
}
```

<div className="h-5" />

Both integers are loaded straight out of the mapped file with a pair of 8-byte
`memcpy` calls, then masked down to just the station name. We read all 16 bytes
regardless of how long the name is, but we can mask any bytes that run past the
name if we know the position of the delimiter that follows it (more on
optimizing this later). Reading only as many bytes as the name actually occupies
would mean either branching on the length or handing `memcpy` a runtime size,
which it can no longer fold into a pair of loads (for more on this, read
[here](https://www.learncpp.com/cpp-tutorial/the-as-if-rule-and-compile-time-optimization/)).
Reading the maximum costs two `and` instructions instead, and since every name
is followed by a delimiter and a reading, the bytes we overshoot into are still
part of the same line. Note that the 9 possible bytemasks can be computed at
compile time, one for each number of bytes (0 through 8) the name can occupy in
either integer.

<div className="h-5" />

Putting the fixed-size keys, the compile-time masks, and the new hash function
together, we get another great performance improvement over the previous
iteration:

<div className="h-5" />

$$
\begin{array}{|l|r|}
\hline
\textbf{Metric} & \textbf{Value} \\
\hline
\text{Wall clock (s)} & 0.92015 \pm 0.00173 \\
\text{Context switches} & 79 \\
\text{Page faults} & 66{,}721 \\
\text{Instructions per cycle} & 0.88 \\
\text{Effective clock (GHz)} & 3.97 \\
\hline
\end{array}
$$

$$

The instruction count fell from 65 billion to 36 billion and instructions per

while we do it.

## **Optimization 2**: SIMD / SWAR

Going back to the naive approach, each thread found the delimiters on a line
with `std::ranges::find`, which walks the line one byte at a time, comparing
each character against the delimiter and branching on the result. Branch
mispredicts can cost us a lot of clock cycles, so it is in our best interest to
remove them when possible. One look at `perf report` revealed that nearly 20% of
the program's clock cycles were spent within these searches, so it made sense to
turn to SIMD instead. Most CPU cores come with a set of wide registers that
allow a single instruction to operate on several values at once, and the
i5-10400 on my workbench has sixteen 256-bit registers through AVX2. Since a
station name is at most 15 bytes, the name and the semicolon that follows it
always fit within the 32 bytes that one of these registers holds. So, instead of
checking one character at a time, we can load 32 bytes of the line into a
register, compare every byte against a semicolon in a single instruction, and
reduce the result to a 32-bit mask whose lowest set bit marks the position of
the delimiter. The same trick finds the newline, and neither search loops nor
branches per character. In the best case, a single load could find the
delimiters of $$\lfloor \tfrac{32}{6} \rfloor = 5$$ readings at a time (more on
this later).

<div className="h-5" />

A SIMD load from L1 usually takes between 5 and 7 cycles on AVX2, which is a
small price to pay for the boost in processing throughput.

<aside className="mt-6 rounded-md border-l-4 border-amber-400 dark:border-yellow-500/70 bg-amber-50 dark:bg-yellow-900/30 p-4">
  <div className="mx-2" />

**Aside: Speculative Read-ahead**

  <div className="mt-2">

It is important to discern the OS's behavior when it comes to loading the mapped
file into memory. As it turns out, there is functionality for
[prefetching pages of the mapped file](https://stackoverflow.com/questions/19653618/mmap-will-the-mapped-file-be-loaded-into-memory-immediately).
Linux provides a configurable variable named `read_ahead_kb` that denotes how
many kilobytes of a file the kernel can fetch into the page cache in advance.
This value is 128 by default, or 32 pages. Normally, this allows for reading on
both sides of the faulting address. However, by alerting the kernel that we will
access these pages sequentially via the system call
[`madvise(MADV_SEQUENTIAL)`](https://man7.org/linux/man-pages/man2/madvise.2.html),
it instead reads ahead only in the direction we're scanning. Note that this only
matters on a cold run, since a warm run finds every page already in the page
cache.

  </div>
</aside>

Note that instructions per cycle actually fell from 0.88 to 0.64, which looks
like a regression at first glance. However, the instruction count fell from 36
billion to 23 billion, so we're doing far less work overall. Branch mispredicts
fell from 710 million to 196 million too, even though a larger percentage of
branches now mispredict, since the total number of branches dropped from 11.6
billion to 1.7 billion. This solved part of the branch mispredict issue, but we
are still mispredicting $$\approx 11.33 \%$$ of all branches.

<div className="h-5" />

The remaining branch mispredicts are still the glaring issue here, even after
improving our delimiter search. I had reason to believe, from more digging
through `perf report` that most of them came from parsing the temperature, which
checks for a minus sign and for whether the reading has one or two digits before
the decimal point. Since the temperature readings in the input are generated at
random, I originally figured neither check could be predicted reliably. The fix
I found
[here](https://github.com/merykitty/1brc/blob/1a4ac0d2496e9329534370eaf01b28e77658b073/src/main/java/dev/morling/onebrc/CalculateAverage_merykitty.java),
from another programmer attempting the same challenge used SWAR (SIMD within a
register), which applies the same idea as SIMD to an ordinary 64-bit
general-purpose register. A reading is at most 6 bytes long (`-99.9` and the
newline), so the entire reading fits into a single 8-byte load and its value can
be pulled out with some bit manipulation and a single multiplication, without
branching on the sign or the number of digits. I still don't understand fully
how this works; it is quite the feat. Credit to
[merykitty](https://github.com/merykitty) who pioneered the method.

<div className="h-5" />

The catch with this approach that doesn't pair well with the previous
optimization is that SWAR lives in a general-purpose register, not the vector
registers that we just used to find the delimiters. Parsing a number depends on
where each of its digits sits, and each reading starts at a different offset
within the register, so AVX2 provides no easy way to line them up in lanes and
parse several at once. To solve this, we have the SIMD search only return the
position of the semicolon, and the 8 bytes after it are loaded again into a
general-purpose register to be parsed one reading at a time (If there is a
clever way to work around this double load, please let me know). SWAR also finds
the end of the line on its own, since the newline always sits two bytes after
the decimal point, which makes the SIMD search for the newline redundant.

<div className="h-5" />

My implementation can be found
[here](https://github.com/artiehumphreys/1brc/blob/main/include/utils.hpp#L79).

Surprisingly, the program got slower: the wall clock rose from 0.822 seconds to
0.855 seconds, even though branch mispredicts fell from 196 million to 166
million. However, the disassembly revealed that the `std::min` call used to
split the station name across the two 8-byte integers had compiled to a branch.
Since station names vary randomly in length, that branch was responsible for the
vast majority of the remaining mispredicts.

<div className="h-5" />

```cpp
// bytes 0-7 of the name go in s0, bytes 8-15 in s1
const size_t sep = std::min(station_length, size_t{8}); // compiles to a branch
// extract relevant bytes for station name
s0 &= station_masks[sep];
s1 &= station_masks[station_length - sep];
```

<div className="h-5" />

As for why the program got slower with fewer mispredicts, I believe it comes
down to a control dependency versus a data dependency. A branch can be
speculated past, so when the CPU guesses correctly, the check costs next to
nothing, and the digit check would have been guessed correctly about 90% of the
time. A branchless computation can't be speculated past, so every reading now
pays the full cost of the bit manipulation, and the branchless version even
executes slightly more instructions, 23.4 billion versus 23.0 billion.

<div className="h-5" />

To get rid of the `std::min` branch, I replaced the 9 single masks with a lookup
table of mask pairs, one for each possible name length. The previous version had
to compare the length against 8 to decide how the name splits across the two
integers before it could look up either mask. The new table bakes that split
into every entry, so a single lookup by the full length returns both masks and
nothing compares against the length at all:

<div className="h-5" />

```cpp
// one {low, high} mask pair per name length, built at compile time
const StationNameMask station_name_mask = station_masks[station_length];
s0 &= station_name_mask.low_bytes;
s1 &= station_name_mask.high_bytes;
```

<div className="h-5" />

Running this against the same input:

<div className="h-5" />
